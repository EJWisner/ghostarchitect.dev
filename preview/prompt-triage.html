// the problem nobody is solving

Your team reviews code in pull requests.
Who reviews the prompts?

If you ship AI features, your prompts are running in production. They route customer interactions, shape outputs, and burn API tokens every time they misbehave. Most teams have no review process for prompts at all. The engineer who writes a prompt usually deploys it, and there is no second set of eyes on the file behind thousands of model calls a day.

Prompt Triage™ is the second set of eyes. It reads every prompt file you point it at and flags the defects the published research identifies as causes of unpredictable model behavior: ambiguity, conflicting instructions, token overflows, undefined output formats and injection patterns. The bugs that make your AI hedge, wander or run away with your budget.

// the 16 detectors

What Prompt Triage™ catches.

Seven checks cost nothing to run and never leave your machine. Nine more use a model you choose, and you see the cost before any call goes out.

No model · no cost

Formatting

Unclosed code blocks, unclosed inline code, broken tags, unmatched close tags, multiple system blocks, mixed role conventions, stray line markers.

No model · no cost

Length

Prompts too short to be useful or too long to be efficient. Severity scales with how far off they are.

No model · no cost

Runaway output

Finds the instructions that let the model write until your budget runs out: no length cap, no format constraint, no stop condition.

No model · no cost

Injection patterns

Known prompt injection patterns: instruction overrides, jailbreak phrases, exfiltration attempts, caught without a model call.

No model · no cost

Role separation

System, user and assistant boundaries that bleed into each other, and mixed message conventions that confuse the model about who is speaking.

No model · no cost

Token limit: context overflow

Prompts plus expected output that exceed your target model’s context window, flagged before runtime.

No model · no cost

Token limit: excessive

Prompts that use an unreasonable share of the context window for their job. A sign of bloat you pay for on every call.

Model-judged

Ambiguous instruction

Instructions a careful reader could take two ways: vague verbs, hedge words, missing acceptance criteria.

Model-judged

Underspecified constraints

Tasks missing the boundary conditions the model needs: edge cases, failure modes, examples of done.

Model-judged

Conflicting instructions

Two parts of the same prompt asking for opposite things. The model hedges, the output gets longer, your token bill climbs.

Model-judged

Undefined output format

You expect JSON or a structured response but never said so. The model picks a format, your parser breaks, you retry.

Model-judged

Overloaded prompt

One prompt asking the model to do five things at once. Splitting it into a chain is often cheaper and better.

Model-judged

Poor organization

Instructions scattered, context buried, important constraints at the bottom. The model follows rules it can see clearly.

Model-judged

Inefficient few-shot

Examples that do not show what you want, contradict each other, or bloat the prompt without teaching the model anything.

Model-judged

Poor documentation

Prompts written for their author, not for the next engineer who has to debug them. A maintenance cost at scale.

Hybrid

Integration mismatch

The prompt declares one output format but its examples use another, or tool schema field names drift from the instruction text. The bugs that break integrations silently.

// backed by published research

The taxonomy is not ours. We put it to work.

The 16 detectors are derived from Tian et al. 2025, an academic survey of the prompt defect categories behind unpredictable LLM behavior. Each detector targets a distinct defect class from that research, with an explicit reference to its taxonomy entry. So Prompt Triage™ is not offering opinions about your prompts; it flags patterns the published research identifies as causes of trouble.

// the savings story

What clean prompts save you.

Prompt defects are not abstract quality issues; each one is a cost driver. Ambiguity causes retries. Conflicting instructions cause hedged, longer output. Undefined output formats cause parse failures and retries. Unbounded outputs cause runaway token bills. Token overflows cause failed requests. It compounds across every prompt in your stack.

Lower API bills

Every defect it finds is one you can fix before it bills you on every call: bounded outputs cap runaway costs, and clear output formats mean fewer retries from broken parses.

More predictable behavior

Catch ambiguity and conflicting instructions before they ship, so production behaves more like what you tested.

No surprise costs

Every model-judged scan shows the cost band first. Confirm or cancel before you spend a cent. No mystery model calls, no bill shock at the end of the month.

Your key, your bill

Faster review

Prompts that pass are easier to review: documentation, structure and constraints already checked. Your seniors spend less time decoding what a prompt is supposed to do.

A quality story you can defend

// frequently asked

Common questions.

How accurate are the detectors?

The seven no-model checks are rule-based and deterministic, so they are as accurate as the rule. The model-judged checks depend on the target model you pick: a larger model judges more carefully and costs more per prompt. Our live test used Claude Haiku 4.5.

What does a scan cost?

If you do not pick a target model, only the seven no-model checks run, and they cost nothing. With a target model, our live test of 7 prompts on Claude Haiku 4.5 came to $0.41 in total, about six cents a prompt. Ghost Open™ shows the cost band before any model call fires and reports the actual spend after the scan.

What file formats does it support?

Markdown (.md, .markdown), plain text (.txt), YAML (.yaml, .yml) and JSON (.json) files with prompt content. It filters out non-prompt files automatically (package.json, tsconfig, lockfiles and so on), so you can point it at a project root.

Does Prompt Triage™ send my prompts anywhere?

The seven no-model checks run entirely on your machine. The model-judged checks send prompt text to Anthropic’s API on your own key, under your own agreement with Anthropic. We run no server that receives your prompts.

Can I run Prompt Triage™ in CI?

Yes. Pass --non-interactive on the CLI to skip prompts. The cost check is auto-confirmed when a budget cap is set, and the exit code reflects whether any Critical findings came up, so CI can fail a build on a regression.

What is the difference between Ghost Open™ and Ghost Architect™ Local for Prompt Triage™?

Ghost Open™ runs Prompt Triage™ as a one-shot audit for one person: every scan stands alone, every report is full. Ghost Architect™ Local adds project tracking: label a scan with a project name, and later scans on that label show which findings were resolved, which remain and which are new, with the project’s scans together on the Project Dashboard, across a team, on your own model. If you track prompt quality week to week across a team, Local is the upgrade. For one-off audits, Ghost Open™ is enough.

How is this different from a linter?

Linters catch syntax issues. Prompt Triage™ also catches semantic defects (ambiguity, conflicting instructions, undefined contracts, integration mismatches) that do not show up in syntax. The seven no-model checks are linter-style; the nine model-judged and hybrid checks find problems a rule cannot see.
