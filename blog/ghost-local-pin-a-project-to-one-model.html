One client, one model, every time

Since 8.1.2, an administrator can pin a project to one local model. Every model call of that project's scans then runs on that model, on whichever machine in your cluster serves it, and never on another.

Load balancing is the right default. A scan should run wherever there is room. But some projects need the opposite promise. When you compare this month's report with last month's, you want the difference to be the code, not a different model on a different machine. When a report may be read by counsel, you want to say which model wrote every word, and that it was the same model each time.

What a pin does

  • Every call on the pinned model. On whichever machine in your cluster serves it. Every project you do not pin is load balanced exactly as before.
  • Wait or refuse, never a substitute. With each pin you choose what happens when no machine can take a call on that model: the call waits for it, which is the default, or the scan is refused. A pinned call never runs on another model: not this hub's, not a fallback, not the cloud.
  • Reuse stays honest. A pinned project reuses only the passes and answers its own model wrote. Anything another model wrote is asked again, on the pinned model.
  • Spokes follow the pin. A spoke asks its hub for the project's model and follows it.

Said everywhere

The Dashboard shows each project's model. The Scan Queue says why a pinned call is waiting. The scan log has a line for every call, the Fleet page lists the pinned projects, and the report says "Project model: ... every call ran on it", counted from the calls the scan actually made.

For agencies

Serve one client on a larger model and another on a faster one, from the same hub and the same queue. Set the pin on the project's page in the portal, with ghost --project-model, or through the REST API. Every change asks for the administrator's password and goes in the audit log.
