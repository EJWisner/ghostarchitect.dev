The passwords people actually choose

An API key looks like an API key. A password a person chose looks like a word, a year and an exclamation mark. That is why most tools that strip secrets from code miss the one that opens your production database. Over the last week of releases, we went after exactly that password.

Why it matters to you

A database password in a config file, a deploy script or a test fixture is the secret most likely to sit in a codebase, and the one that does the most damage when it travels. When Ghost Architect™ Local sends your code to a model, or writes a report you hand to a client, that password should not be in it. Before this work, in most of the places it is written, it was.

Found where it is written, not by what it looks like

A chosen password has no shape to match, so Ghost reads the line around it: the name beside it, the command it is handed to, the SQL statement that sets it. We measured that one form at a time. Nine passwords a person might choose, run through 156 ways a password is written in code, commands, SQL, settings files and documents: before 8.1.20 your model was shown every one of them in 92 of those forms. After it, none of them in 148.

8.1.21 added 112 more forms: a fallback after reading the environment, a method that sets the password, a value handed to docker run, helm or a systemd unit. 8.1.22 caught passwords that hold a quote written with a backslash, as JSON and most code write them: part of one was shown in every one of 130 forms before, and none is shown in any after. 8.1.34 caught a password that ends in a backslash in SQL and in Windows batch files.

Nothing it replaced before is shown now

Every one of these releases only adds. Each new reading runs after everything the release before does and reads only what it left, so a file is never shown more than it was. For 8.1.34 we checked that against the release before on more than 60,000 lines drawn at random from the forms.

What it still leaves, on purpose and not

A path to where a password is kept, a version number, a hash, a value under a name that says it holds something else (forgot_password, MIN_PASSWORD) are left as written on purpose, because redacting them would hide code you need reviewed. A password inside a string inside a string, such as JSON written inside code, is not covered yet; it is our next release. Chapter 6 of the manual lists what each form leaves. We would rather you know the limits than find them.

Check it on your own hub

ghost --redaction-check plants fresh fake passwords in many of these forms, scans them in every mode on your own machine, and searches everything Ghost wrote, printed and sent. Its dated report says what a passed run does and does not show.
